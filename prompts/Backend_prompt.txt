Enhanced BeeHyv Project Review Prompt — E4H Digital Platform

Assume the system is production-bound or already running in production.

================================================

PROJECT CONTEXT (MANDATORY — FILL BEFORE REVIEW)

The E4H Digital Platform backend is designed to:

- Provide the microservices backend for Selco Foundation's Energy for Health (E4H) program, built on the DIGIT/eGov framework
- Expose REST APIs (Spring Boot) consumed by the frontend and mobile clients, fronted by a Zuul gateway
- Persist domain data in PostgreSQL, using JdbcTemplate/JPA repositories with Flyway-managed schema migrations
- Support multi-tenancy via tenantId across services (data isolation between tenants/deployments)
- Publish and consume events over Kafka for async workflows, notifications, and audit/event tracking
- Integrate with shared core-services (egov-workflow-v2, egov-filestore, egov-idgen, egov-mdms-service-v2, egov-notification-sms, boundary-service, health-facility-registry)
- Implement domain-specific e4h-services (field-planner, asset-registry, egov-hrms, im-services, ingestion-service, processor-services, project, rms-service, vendor-registry, translator-service, amc-scheduler-service, inbox, field-planner-activity)
- Handle retries/idempotency for cross-service calls and Kafka consumers
- Enforce role-based access via egov-user/RBAC and request validation via RequestInfo/ResponseInfo contracts

Use README.md and the codebase (backend/core-services, backend/e4h-services, backend/municipal-services) for more context.

PROJECT REVIEW CHECKLIST (USE AS EVALUATION CRITERIA)

Do NOT quote this checklist in the output.
Use it to guide analysis.

### Product Intent & Architecture Fit

- System purpose clear from code and README
- Clear component/module boundaries (core-services vs e4h-services vs municipal-services)
- Architecture appropriate for a multi-tenant, multi-service eGov platform
- Multi-tenancy (tenantId) consistently enforced across controllers, services, and queries

### Git Discipline & Engineering Maturity

- Branching strategy visible (main/develop/release, per CODEOWNERS ownership)
- Small, meaningful commits
- Evidence of reviews and controlled merges

### Code Health & Implementation Details

- Detect Logic Bugs:

  - Off-by-one errors
  - Incorrect boolean logic
  - State inconsistency

- Variable Scope:

  - Variables defined in the narrowest possible scope.

- Separation of Concerns:
  - Controller (web layer) not mixed with SQL/query-builder or Kafka producer logic
  - Query builders isolated from repository/JdbcTemplate execution

### Resource Management & Memory Safety (CRITICAL)

- Resource Cleanup:

  - Are try-with-resources or finally blocks used for all JDBC Connections, PreparedStatements, ResultSets, and file/MultipartFile streams (e.g. egov-filestore uploads)?

- Memory Leaks:

  - Look for static maps growing unbounded.
  - Listeners/Kafka consumers not properly closed.
  - ThreadLocal misuse (must be static and cleaned up — check RequestInfo/tenant context holders).

- Object Lifecycle:
  - Are heavy objects (DataSource/HikariCP pool, Kafka Producer, ObjectMapper) injected as singletons and reused?
  - Are they recreated unnecessarily per request?

### Concurrency & Thread Safety

- Thread Safety:

  - Are non-thread-safe objects (SimpleDateFormat, ArrayList, etc.) shared between request threads or Kafka consumer threads?

- Shared State:

  - Is state correctly synchronized or immutable across concurrent requests/consumers?

- ThreadLocal Usage:
  - Are ThreadLocal variables static final?
  - Is remove() guaranteed to run (e.g. in a finally block or filter)?

### Failure Handling & Defensive Design

- Errors not swallowed (no empty catch blocks around JDBC/Kafka calls).
- Stack traces preserved; CustomException used consistently with meaningful error codes.
- Atomicity maintained (transaction boundaries around multi-table writes).
- Retry/backoff for Kafka publish failures and inter-service calls (e.g. workflow, filestore, mdms).

### Runtime Observability

- Structured, meaningful logs (trace/debug/info consistent with existing services).
- Correlation IDs / RequestInfo propagated across service calls.
- Correct log levels.
- No secrets, tokens, or PII (patient/beneficiary data) in logs.

### Data Access & Persistence Safety

- Connection pool used (HikariCP via Spring Boot datasource) — no manual DriverManager.getConnection.
- Parameterized queries via JdbcTemplate/PreparedStatement (no string-concatenated SQL) — check query-builder classes specifically.
- Transaction boundaries clearly defined (@Transactional where multi-step writes occur).
- Flyway migrations reviewed for backward compatibility (no destructive changes without a rollback path).

### Configuration & Secret Hygiene

- No hardcoded secrets, DB credentials, or Kafka broker URLs.
- Externalized configuration (application.properties/yml, environment variables, Helm/K8s config).
- .env and local secrets ignored via .gitignore.

### Testing Strategy & Confidence

- Unit tests for core service/business logic.
- Integration tests for critical paths (search, create, update, Kafka consumers).
- Tests executed in CI (.github workflows).

### Performance & Scale Readiness

- Identify bottlenecks:
  - N+1 queries across service-to-service calls (e.g. per-record lookups instead of batch/mdms bulk fetch)
  - Blocking calls to other services on the request thread
  - Missing pagination on `_search` endpoints (limit/offset/URLParams)
  - Missing caching for reference/MDMS data

### Dependency & Supply-Chain Health

- Maintained libraries (egov-core, egov-models versions).
- Versions pinned in pom.xml.
- Vulnerability awareness (no known-CVE dependencies).

### Project Structure & Formatting

- Standard Java/Spring Boot Maven structure, consistent with sibling services under e4h-services/core-services.
- Consistent naming (controllers, services, repositories, query builders).
- Consistent formatting.

REVIEW MINDSET

- Hunt for bugs first.
- Then review architecture (service boundaries, multi-tenancy).
- Scrutinize static fields.
- Scrutinize ThreadLocal usage.
- Scrutinize JDBC connections and Kafka producer/consumer lifecycle.

Immediately flag:

- new ThreadLocal<>() that is not static.
- Missing ThreadLocal.remove().
- DriverManager.getConnection() inside loops or request paths.
- Missing connection pooling.
- Kafka producers/consumers not closed or leaking threads.
- `_search` endpoints missing tenantId filtering or pagination.

Be direct.
Be actionable.
